# MVP Overview — Phased Feature Plan

Companion to [`PROJECT.md`](../../PROJECT.md). That file says *what* Fantasy Assist is and
how it's structured; this file says *in what order we build it*.

**Sequencing principle:** every phase ends with something you could actually open and use.
Phase 2 is already a usable draft board; everything after it makes it better, not merely
more complete.

**Phase 0–3 = the MVP.** Phases 4–5 are post-MVP and should not be started until the MVP is
in use during a real draft.

---

## Phase 0 — Foundation

*Goal: an empty app that builds, tests, and deploys. No features.*

| # | Item | Detail |
|---|---|---|
| 0.1 | Scaffold | Vite + React 19 + TypeScript (strict) |
| 0.2 | Styling | Tailwind v4, design tokens (colour, spacing, radius, type scale) defined once |
| 0.3 | Directory skeleton | Exactly the layout in `PROJECT.md` §5 — empty dirs with an index barrel |
| 0.4 | Tooling | ESLint + Prettier, Vitest + RTL, `typecheck` script |
| 0.5 | Scripts | `dev`, `build`, `test`, `typecheck`, `lint` — then fill in `PROJECT.md` §7 |
| 0.6 | App shell | Header, main region, empty state. Renders. Nothing else. |

**Done when:** `npm run dev` serves a styled empty shell; `build`, `test`, `typecheck`, and
`lint` all pass clean.

## Phase 1 — Data layer

*Goal: real 2026 rankings loaded into a typed domain model. Still no interactivity.*

| # | Item | Detail |
|---|---|---|
| 1.1 | Domain types | `Player`, `Position`, `Format`, `BoardState` in `domain/player.ts` |
| 1.2 | Dataset schema | JSON shape + provenance block (`source`, `sourceUrl`, `retrievedAt`, `season`) |
| 1.3 | Redraft PPR 2026 | `src/data/rankings/redraft-ppr-2026.json`, 426 players |
| 1.4 | Dynasty SF 2026 | `src/data/rankings/dynasty-sf-2026.json`, 439 players, includes `age` |
| 1.5 | `RankingSource` adapter | Interface + local-JSON implementation. The only ingestion seam. |
| 1.6 | Validation | Parse-and-throw on malformed data: duplicate ids, unknown position, rank gaps |
| 1.7 | Static render | List the loaded players, read-only, no styling ambition |

> **Unblocked (2026-08-18) — see `PROJECT.md` §3.** The earlier "rankings are paywalled"
> finding was wrong: Flock serves its consensus rankings from a public, unauthenticated API.
> Items 1.3 / 1.4 ship **real 2026 data**, generated by `npm run fetch:rankings` and committed.
> No placeholder dataset was needed, and no hand-supplied input is outstanding.

**Done when:** both formats load, validate, and render as a static list; a corrupt dataset
fails loudly at startup.

## Phase 2 — Core interactivity *(this is the usable product)*

*Goal: the three headline features. After this phase you could draft with it.*

| # | Item | Detail |
|---|---|---|
| 2.1 | Board store | Zustand: `order`, `drafted`, per-format, with selectors |
| 2.2 | Persistence | `localStorage` read/write, schema-versioned so future changes can migrate |
| 2.3 | **Cross off** | One click toggles drafted; row greys, strikes through, and de-emphasises |
| 2.4 | Availability filter | Show all / available only. Available-only is the default. |
| 2.5 | **Reorder** | Drag-and-drop via dnd-kit, plus keyboard move (↑/↓ on a focused row) |
| 2.6 | Rank display | Your rank vs. `baseRank`, with a delta indicator when you've moved someone |
| 2.7 | **Position filter** | QB / RB / WR / TE / K / DST tabs + "All"; reordering stays coherent while filtered |
| 2.8 | Format switch | Redraft PPR ↔ Dynasty SF; each format holds its own independent edits |
| 2.9 | Search | Substring match on name and team, instant |
| 2.10 | Reset | "Reset to expert rankings" and "Clear drafted", both confirmed |

**Done when:** you can reorder, cross off, filter, search, switch formats, and refresh the
page with every edit intact.

**Design note for 2.7:** reordering *inside* a filtered view must map back to the full
`order` array without disturbing the relative position of hidden players. Handle it in
`domain/board.ts` where it's unit-testable — not in the drag handler.

## Phase 3 — Draft-day polish *(completes the MVP)*

*Goal: make it pleasant and safe to use under time pressure.*

| # | Item | Detail |
|---|---|---|
| 3.1 | Undo / redo | Snapshot-based, keyboard-bound. The safety net for a misclick at pick 4.03. |
| 3.2 | Motion | Reorder and cross-off animate; respects `prefers-reduced-motion` |
| 3.3 | Tier bands | Visual grouping by tier, so a tier break is obvious at a glance |
| 3.4 | Density + dark mode | Compact row option; dark theme (a draft runs at night) |
| 3.5 | Responsive | Usable on a phone — thumb-reachable cross-off, no horizontal scroll |
| 3.6 | Accessibility pass | Focus order, ARIA for the sortable list, live region on cross-off, contrast audit |
| 3.7 | Performance | Virtualised list; verify no dropped frames while dragging a 400-row board |
| 3.8 | Export / import | Download and restore board state as JSON — the backup for a browser wipe |

**Done when:** a full mock draft can be run end to end without friction, and a keyboard-only
user can do everything a mouse user can.

---

## Phase 4 — Beyond the MVP

Only after real draft usage tells us which of these actually matters.

- **Custom tiers** — draw your own tier breaks instead of inheriting the source's.
- **Notes** — a short per-player note ("hamstring, monitor Thursday").
- **Watchlist / targets** — star players and filter to them.
- **Positional scarcity** — show how many players remain above a value threshold per position.
- **Multiple boards** — separate saved boards per league, not just per format.
- **Bye-week view** — surface bye collisions among your drafted players.
- **Dataset refresh** — drop in an updated ranking file and reconcile it against your edits
  (new players added, retired players removed, your `order` preserved).

## Phase 5 — Speculative

Not planned. Recorded so they don't get invented mid-build.

- Sleeper / ESPN / Yahoo league sync (would require a backend and OAuth).
- Multi-user shared boards (would require accounts).
- Projections, trade values, start/sit (out of scope per `PROJECT.md` §1).
- Licensed rankings API integration — only if a provider offers legitimate access; the
  `RankingSource` adapter already leaves the seam for it.

## Dependency map

```
Phase 0 ──▶ Phase 1 ──▶ Phase 2 ──▶ Phase 3 ──▶ Phase 4 ──▶ Phase 5
foundation   data        core         polish      extras     speculative
                          ▲
                    MVP is usable here
```

Nothing in Phases 2–3 can start before Phase 1's domain types exist. Within Phase 2, 2.1–2.2
gate everything else; 2.3–2.10 are independent of each other once the store exists.
